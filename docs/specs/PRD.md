## 1. 产品概述

### 1.1 产品定位
听序（Tingxu）是一款专为中国大陆职场个人打造的极简桌面 AI 会议助手。通过纯本地免驱动底层音频捕获、流式语音识别（ASR）与大模型增量提炼，在不向会议软件（Teams、腾讯会议、飞书、钉钉、Zoom 等）添加任何虚拟参会机器人的前提下，实现会议全程“边开会、边理解、边整理”。

### 1.2 产品目标
1. **解放双手**：大幅降低用户在会中一边听、一边手工打字记笔记的认知负担。
2. **结论与行动项对齐**：通过会中实时洞察看板与主动问答，帮助参会者及时捕捉关键决定、数字承诺与遗漏待办，避免会后推诿扯皮。
3. **数据主权与隐私保障**：会议音视频、逐字稿与纪要全生命周期本地优先存储（Local-First），消除企业商业机密被第三方云端留存的顾虑。
4. **低门槛商业闭环**：以明确的“会议时长套餐”提供服务，标准 AI 能力（实时洞察、会后纪要、本场问答）全部打包入套餐，提供无隐形扣费的良好口碑。

### 1.3 目标用户与画像
- **核心用户**：产品经理（PM）、项目经理（PMP / Scrum Master / 研发管理人员）。
- **扩展用户**：独立顾问、售前方案专家、咨询分析师、高频参与跨部门沟通的业务骨干。
- **用户特征**：
  - 每天有 2-5 场线上会议，会议跨度长、信息密度大；
  - 经常需要撰写并分发会议纪要、跟进 Action Items；
  - 对在公开会议中“拉入一个 AI 录音机器人”感到社交尴尬或受限于企业安全合规策略；
  - 极度看重会议内容的私密性与本地可控性。

### 1.4 核心价值主张
- **免机器人（No Bot）**：不打扰他人，免装第三方声卡驱动，双端原生捕获。
- **物理双轨识别（Dual-Track）**：本地麦克风与系统扬声器硬件级分流，从源头彻底区隔“我”与“对方”。
- **边开会边整理（In-Meeting Insights）**：打破“会后等几分钟全盘跑大模型”的传统模式，会中以结构化看板动态刷新决策与待办，并提供本场问答。
- **证据可回溯（Evidence Anchoring）**：任何 AI 提取的事实均附带原文段落引用，一键高亮跳转，避免大模型幻觉误导。

## 2. 业务背景与市场定位

### 2.1 项目背景
现有会议记录工具往往存在两大约束：
1. **机器人形态方案（如腾讯会议 AI、部分开源方案）**：必须向会议室注入机器人账号，这在多方商务谈判、涉及保密讨论的跨组织会议中常被主持人踢出或引发合规争议。
2. **后处理型录音工具（如多数录音笔软件）**：只能在会后上传整段音频，需要等待漫长的识别和总结过程，无法在会中直接发挥辅助思考、补充遗漏信息的作用。

### 2.2 竞品对比与差异化

| 维度 | 听序 (Tingxu) | 讯飞听见桌面端 | Granola (海外) | 飞书/腾讯会议自带妙记 |
| --- | --- | --- | --- | --- |
| **入会方式** | 物理双轨内录（免机器人） | 系统音频录制（免机器人） | 本地免驱捕获 | 平台内建录制 / 机器人入会 |
| **多平台支持** | Windows + macOS 同步支持 | Windows 为主 (Mac 支持弱) | 仅 macOS (早期) | 全平台，但依赖平台自身会议 |
| **会中交互** | 实时看板 + 本场问答 + 逐字稿 | 逐字稿为主 + 简单打点 | 手记优先 + 侧边栏结构化整理 | 主要是实时滚动逐字稿 |
| **数据存储** | **Local-First (本机存储)** | 云端同步存储 | 本地与云端混合 | **纯云端留存** |
| **商业模式** | **会议时长套餐（AI 全包）** | 转写时长卡 + 复杂服务 | 个人订阅 ($10-20/月) | 捆绑企业版套件 |

### 2.3 成功衡量指标（KPIs）
- **首次成功记录率** $\ge 95\%$（从安装、授权到完成第一次 5 分钟测试记录的成功转化）；
- **整理采纳率** $\ge 80\%$（生成的 Action Items 与核心决策被用户确认或导出的比例）；
- **任务端到端时延**：会后全局纪要生成耗时 $< 30$ 秒（1 小时标准会议）；
- **系统资源消耗**：桌面常驻内存 $< 60\text{MB}$，开会录音与转写时 CPU 占用 $< 5\%$。

## 3. 核心使用场景与用户故事

### 3.1 核心使用场景
1. **场景一：跨部门需求评审会（PM 主导）**  
   PM 组织研发、测试、运营开需求会。PM 开启听序，屏幕右侧贴边吸附微型悬浮条。会议中讨论到技术难点时，看板实时提炼出“研发指出周五上线有风险，需先做压力测试”。PM 看到后立即在会中追问确认，并在看板中将该结论标记为“已确认”。
2. **场景二：客户商务沟通会（咨询/售前）**  
   客户不希望外来录音设备进入会议。售前人员佩戴耳机，听序纯本地免驱捕获客户发言并标记为“对方”。会中随时在“AI 问一问”中提问“客户刚才提到的预算范围和关键上线节点是什么？”，系统立即给出准确数字并锚定原文时间段。
3. **场景三：无网/离线飞行环境下的复盘与导出**  
   用户在差旅或弱网环境下回顾历史会议，由于会议数据全部保存在本机 SQLite，用户可以在毫秒级检索全文、播放本地录音切片并导出标准 Markdown 纪要。

### 3.2 用户故事清单
- **US-01**：作为产品经理，我希望在不向腾讯会议添加机器人的情况下完整录制会议，以便避免团队被监控的不适感。
- **US-02**：作为参会者，我希望在会中能随时看到当前讨论的核心论点与已达成共识，以便在走神后能快速跟上讨论进度。
- **US-03**：作为项目经理，我希望确认过的结论在后续讨论发生变化时不会被直接覆盖，而是提醒我“有新修订需要核对”，以便防范需求遗漏。
- **US-04**：作为注重隐私的用户，我希望所有会议的逐字稿与录音存放在我的个人电脑上，云端绝不留存任何底稿。
- **US-05**：作为付费用户，我希望购买清晰的会议时长套餐，开会时随意使用实时问答与纪要整理，而不是提一个问题就被扣几点额度。

## 5. 关键业务规则（Business Rules）

- **BR-001【用户授权与数据流向】**：首次使用或涉及云端处理（ASR / LLM）时，必须明确弹出数据流向确认窗口。本地录音与云端 AI 须分别确认，用户未勾选云端授权时仅在本地存储录音，不发起任何网络传输。截图默认仅存本地，绝不默认上传给多模态大模型。
- **BR-002【时长套餐与权益扣减】**：现阶段严格采用**会议时长套餐**计费，标准实时洞察、会后纪要、待办提取与本场问答全量包含在套餐内；系统暂不设立用户端 AI 点数或单次扣点机制。云端服务采用“发起时预占时长配额 $\rightarrow$ 成功后据实按秒结算 $\rightarrow$ 异常失败全额释放未成功阶段”。
- **BR-003【网络异常与录音高保真降级】**：在录音过程中如发生断网或时长配额耗尽，客户端必须继续保持本地双轨录音落盘，不得因为转写或 AI 失败而中断录音。转写断开期间在逐字稿中明确打上“网络中断，云转写暂停”标记，恢复后允许用户确认补转。
- **BR-004【会中增量合并与去重（v0.2）】**：实时洞察引擎仅处理新增的“稳定文本（Finalized Text）”，不得将临时识别波动的短语直接作为决定。新增内容优先合并到当前已有议题卡中更新，禁止每隔几分钟生硬追加一份碎片化小结。
- **BR-005【人工编辑与已确认结论保护（v0.2）】**：被用户标记为“已确认”或经过人工手动修改的卡片受核心保护机制锁死。当后续讨论产生相反事实时，系统生成并列的“修订待复核（Pending Review）”卡片，清晰展示新旧版本与对比证据，由人工决定采用或驳回，严禁算法静默改写人工版本。
- **BR-006【事实证据强关联（Evidence Anchoring）】**：所有事实类洞察、提取的决定与待办，必须挂载可定位的 `evidenceRefs`（包含片段 ID、单调时间戳、原文摘录）。当原文发生更正时，关联证据状态置为需要核验。
- **BR-007【会中本场问答边界（v0.2）】**：会中“AI 问一问”默认仅检索当前会议截至提问时刻已确认的稳定原文，不检索历史会议，不读取本地手记与截图。模型证据不足时必须直接回复“本场讨论尚未提及”，不得猜测心理、情绪或臆测未提及细节。
- **BR-008【会后重整与会中快照分离】**：会后生成的最终纪要是独立处理任务，以全场最新完整逐字稿全局重新组织；会中产生的增量洞察、问答历史与手记自动保存为“会中快照（Live Snapshot）”并入档，不直接把最后一张会中卡片当成最终全场纪要。
- **BR-009【套餐到期与本地资料主权】**：用户套餐到期、停机或额度不足时，仅限制发起新的云端转写与 AI 整理服务，绝不得阻止用户查阅、播放、检索、编辑或导出其保存在本地的已有会议记录。
- **BR-010【彻底删除保障】**：用户在客户端删除会议时，系统需弹窗二次确认，确认后物理抹除本机磁盘上的所有关联音频分片、截图图片、SQLite 记录与全文索引。
- **BR-011【免机器人合法合规提示】**：在会议开始录制前，系统界面必须明确展示录音中指示灯，并附带提示：“请确保您已取得本次会议全体参会人的知情与同意”。免安装机器人属于技术实现方式，不得被曲解为“秘密录音”许可。
- **BR-012【运营补偿审批隔离】**：运营后台对用户赠送会议时长或延长套餐必须提交理由与数量，由系统所有者（Owner）审核通过后方可通过事务入账，禁止单人越权直接修改权益余额；单次操作具备唯一幂等键，防范重复点击。

## 6. 非功能需求（Non-Functional Requirements）

- **NFR-001 数据与隐私边界**：业务服务端数据库、系统链路日志、Sentry 异常监控中**严禁**写入任何用户会议名称、逐字稿正文、音频切片、截图图片、短信验证码或完整手机号。
- **NFR-002 资源占用**：Windows (x64) 与 macOS (Apple Silicon / Intel) 客户端在后台静默运行时代内存占用 $< 50\text{MB}$；开会双轨录制与渲染字幕时 CPU 占用 $< 5\%$。
- **NFR-003 本地持久化可靠性**：录音音频分片按 1-3 秒原子化分块持续刷盘（Flush），即使系统突然断电或程序异常崩溃，重启后能自动校验并恢复崩溃前最后数秒的完整录音。
- **NFR-004 弱网容灾与断线重连**：ASR WebSocket 连接支持指数退避重连；重连成功后通过序列号对齐断点，避免文字重复或错位。
- **NFR-005 界面可访问性与交互**：界面支持系统原生深色/浅色模式无缝切换；所有重要状态提示（如录音中、网络断开、AI 思考中）必须采用“颜色 + 清晰中文文本”双重表达。

## 8. 实施门槛与上线前决策事项

在正式向中国大陆个人用户推送商业化收费版本前，必须逐项完成以下决策与验证闭环：

1. **套餐定价与计量细则**：确认正式上线价格、单月包含的会议时长额度、跨月结转规则以及合理使用防滥用规则（如连续单次会议最大时长限制）。
2. **ASR 直连与中继架构评测（ADR-001）**：实测验证供应商（阿里百炼/讯飞）WebSocket 临时 STS 凭据是否具备可靠的服务端并发数封顶与异常断开能力；若不达标，必须切换为受控内存中继架构以杜绝盗刷风险。
3. **音频双轨回声消除（AEC）评测**：测试用户外放扬声器时扬声器声音被麦克风二次录入的干扰程度，必要时引入轻量 WebRTC AEC3 处理，并在界面强化“佩戴耳机开会体验最佳”的引导文案。
4. **macOS Gatekeeper 代码公证与 Windows 签名**：完成 Apple 开发者证书配置与代码公证（Notarization），取得 Windows 软件代码签名证书，确保安装时不弹出“未知发布者”或“已损坏”阻断提示。
5. **合规条款与微信商户号核验**：完善用户隐私协议与免责声明，明确音频数据处理规范；核验微信商户号支付能力的桌面端落地资质。
